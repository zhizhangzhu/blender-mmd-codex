## 先分清缺少哪种阴影

- 投影：人物遮住光源，影子落到地面或其他接收物上，方向必须能由灯位解释。
- 接触遮蔽：鞋底、近地鞋尖附近的窄范围暗部；离地后应自然减弱。AO不能代替长投影。
- 自阴影与受光：手臂、衣服、身体随真实灯光形成明暗；若最终是恒亮Emission，开灯光阴影也不会自动进入人物颜色。

本轮只读探针 `scripts/probe_shadow_grounding.py` 在五个姿态记录了灯光、响应节点、脚骨与脚下表面。旧工程的EEVEE阴影已开启，问题并非一个总开关：大面积柔光稀释了主投影，人物响应区间也很容易饱和到亮色。旧布料最低响应0.82、头发0.88，而身体皮肤和脸一起被保护到0.98。骨骼脚踝高于地面不能证明鞋底悬空，因此没有按脚踝位置移动角色或改动作。

## 当前阴影预设

接地起点参数 `presets/stages/hesperides-grounded-shadows-v1.json`，生成器 `scripts/prepare_grounded_shadows.py`；最终人物受光由 `presets/quality/duet-graphic-self-shadow-v1.json` 覆盖，见后面的自身阴影说明。以下是当前礼堂和人物尺度的实测参数，不是通用瓦数。

| 部分 | 本轮实现 | 目的 |
| --- | --- | --- |
| 定向主投影 | 复用grounded light，移到(-3.5,-4,5.5)，指向(0,0.6,0)，1500W、70°、半径0.08 | 与人物前左方主光协调，让地面出现可读投影 |
| 投影范围 | 保留双人人物网格的shadow blocker集合 | 控制人物落影；这属于美术化光照链接，不冒充完整物理照明 |
| 近地AO | 距离0.15、强度0.4、16samples | 补鞋底与近地表面的接触层次 |
| 地面掩码 | 世界坐标abs(Z)<0.2，表面法线Z>0.9 | 避免共享同一材质的墙面、柱子整体变脏 |
| 最终人物受光 | 输入0.18–0.28；布料最低0.60、头发0.70、身体皮肤／脸0.68；面部平整探针法线 | 保留SDF，增加实际遮挡，避免脸部几乎不受阴影影响 |

AO乘到响应场景材质的BaseColor上，因此它是有范围的美术接触修饰，不是无偏物理GI。没有使用粘在脚底的黑色圆片，没有把全图压暗，没有修改原舞步来迁就阴影。灯光修改后重新烘焙静态礼堂GI；人物不参与静态探针烘焙，恢复后正常渲染。既有EEVEE体积阴影仍关闭，新增的是表面投影与接触层次，不能宣称修好了完整体积阴影。

Blender 5.2使用本机实际API和虚拟阴影贴图；不要照搬旧EEVEE教程的Contact Shadows按钮位置。[Blender灯光手册](https://docs.blender.org/manual/zh-hans/4.5/render/eevee/light_settings.html)讨论光源半径、抖动与过滤的取舍。当前没有额外扩大滤波以掩盖问题；灯源越大，投影可能越难在多柔光场景读清。

最终 `production-v3` 同一4250帧有“主灯投影关”和“接触AO关”两张原生控制，其他灯光保留；4290帧另有自身投影关闭与旧线宽控制。控制差异证明效果实际进入渲染，不是效果质量或参考相似度评分；采样变化未完全隔离，因此不将全部像素差异都归于单一效果。三张静帧覆盖4200、4250、4290；动态还需看完整300帧及字幕切换处。独立重开验证报告 `master-verification-v3.json`，检查十时点姿态／镜头、95张贴图打包及旧归档输出静音。

## 自身阴影：不再让脸部几乎免疫遮挡

猪猪提供的《亲亲小狐狸》近景可见发束间、额头、衣领与手臂的明暗层次；流萤竖屏截图尤其清楚地表现了下巴到脖子、手指到掌心、领口与衣褶之间的分色。后者只有用户截图，未获得其视频链接、工程或完整动态，因此只用作该帧的明暗／线条参考，不冒称看过整个视频，也不据此制作竖屏镜头。

检查当前Genshin Face Factor发现：适配时移除了普通Blender不支持的Goo Shader Info，并把 `Catch Shadows` 固定为0。SDF能控制脸上设计好的明暗，不能自己感知一束刘海正在挡住灯光；仅增强SDF或AO不等于恢复真实发影。原资料见 [festivities / Blender-miHoYo-Shaders](https://github.com/festivities/Blender-miHoYo-Shaders)，原配布主要针对游戏数据，不能把MMD变体直接换材质就当作完整适配。

`scripts/diagnose_actor_light.py` 输出实际未裁切的32位浮点受光AOV和材质类别。4290帧，未平整法线时脸部原生受光的5/50/95分位约为0.071/0.549/1.269；可见旧0.12上限会让大部分区域饱和，而脸部0.95亮度下限又几乎抹掉阴影。AOV用于测量这条特定Diffuse链，不被当作整个NPR成片的物理照度。

直接把所有脸部几何凹凸一起阈值化，会在鼻口和下颌产生不理想的斑块；本轮 `production-v2` 就观察到了这个问题。最终做法是保留上游SDF，用随头部转动的前向向量覆盖“白色Diffuse受光探针”的Normal，让面部基础受光更平整，实际灯光射线仍由当前几何遮挡。平整后的两张脸受光中位约0.65，低端仍有由遮挡形成的区域。身体与头发继续使用原来的表面法线。

`presets/quality/duet-graphic-self-shadow-v1.json` 把这条真实受光分色区间设为0.18–0.28，SMOOTHSTEP过渡；阴影最低因子脸／身体皮肤0.68、头发0.70、衣料0.60。这里乘在线性色彩上，因子不等于最终sRGB显示亮度的同比降低。人物参考主灯尺寸从2.4减到0.65，使发影更可读；舞台大面积柔光保留。没有启用已失去Goo输入的旧Catch Shadows开关，而是独立接入普通EEVEE支持的真实遮挡响应。

在4290帧原生“所有灯光投影关闭”控制里，SDF、法线形体明暗、AO仍保留；重新打开投影后，可以在空的刘海下看到新增阴影。这组控制也会改变场景其他投影，因此脸部等比例裁切单独检查。该方法不是把阴影画死在贴图里，会随当前几何、灯光和动作变化。Shader to RGB属于NPR转换，有与阴影和AO、渲染pass组合的局限，见 [Blender官方节点说明](https://docs.blender.org/manual/en/5.1/render/shader_nodes/color/shader_to_rgb.html)；因此必须验收动态，不能只看一个漂亮静帧。

## 加厚黑线仍须保留模型自己的权重

生成器 `scripts/prepare_graphic_self_shadows.py` 使用现有MMD反向外壳，不叠第二套边缘检测：在本轮修改前的当前顶点线宽权重上，相对增加头发45%、衣物40%、脸／身体皮肤25%、毛领18%、装饰25%。数值是几何权重倍率，不是全画面固定像素线宽；共享顶点取较轻倍率，权重最大1，有明确夹取报告。眼睛、眉毛、睫毛和嘴内材质的倍率保留1，不把纹理内线直接膨胀。

边色改为受控近黑，毛领保留0.9透明度。`graphic_ink_source_weights` 与 `graphic_ink_final_weights` 随工程保存；旧线宽控制保持新边色，因此它只隔离宽度，不能称为完整旧美术版。最终近景应同时核对睫毛与虹膜是否粘连、脸颊轮廓是否连续、头发细缝是否被吃掉；最终横屏检查不能代替竖屏适配。

## 为什么三个播放器不同

截图显示PotPlayer更暗；软件内预览与“电影和电视”较接近。第三张底部还有播放器UI渐暗遮罩，这部分不能拿来判断成片曝光。截图尺寸、停留帧和显示路径也未完全统一，两家接近不构成色准标准。

已经确认我们旧版MP4的range、matrix、primaries、transfer全部unknown，这是导出流程的遗漏，应由制作端修正。但它不能单独证明PotPlayer亮度设置有误。播放器的视频渲染器、色彩管理、显卡视频增强、输入电平解释及Windows显示状态均可能影响观感；当前只读查询没有确定PotPlayer实际的gamma或渲染器状态，因此不做断言，也没有改用户播放器、显卡或系统偏好。

四个概念必须分开：

- Primaries：RGB基色色度；sRGB与BT.709共用这组基色。
- Transfer：亮度编码曲线；sRGB与BT.709并不相同，不能为了填标签互换。
- YCbCr matrix：从RGB转YUV的矩阵；HD视频也不应靠分辨率猜矩阵。
- Range：视频limited电平与RGB full电平如何转换；不是把输入、输出、显卡所有选项一律设Full。

旧版实际像素的两帧重建中601比709更接近原始合成RGB，说明旧流程可能用了601默认矩阵。这是基于实际像素的推断，不能说明PotPlayer的整个亮度差都来自矩阵，也不能把旧601数值只改标签成709。

## 修正后的桌面审片输出

`scripts/review_video_color.py` 统一：full-range display-sRGB RGB24输入→明确BT.709 YCbCr矩阵→limited-range YUV420p；写入BT.709 primaries、sRGB transfer (IEC61966-2-1)、BT.709 matrix与TV range。保留源sRGB的实际编码曲线。这是SDR电脑审片约定，不能叫BT.1886调色监看母版；未来广播／平台交付应另做真实曲线变换和平台验证。

本机FFmpeg7.1实测：仅使用输出`-color_primaries`和`-color_trc`，经scale后仍解码为unknown。增加filter中的`setparams`后，H.264解码实际读到完整四项；不能仅凭命令里写了参数便宣称标签正确。

`scripts/verify_review_color.py` 同时检查编码图像和最终混音MP4的实际解码标签。`scripts/audit_review_color.py` 用原生PNG16加同帧官方字幕重建RGB，再分别强制601、709解码比较，以验证矩阵与像素一致。新无字幕版也从PNG16 beauty重新编码，避免给旧的未知矩阵视频强贴709标签。

首次诊断文件位于 `D:\codex\output\MMD-Color-Playback-Audit-v1`：`Franken_Wedding_ColorTags_Only_TEST.mp4`对旧流只补元数据，全部300帧解码YUV校验一致，用于隔离“同一像素、不同解释”。它是诊断，不是最终阴影改版；原视频保留。随后显式709试验v1漏primaries/TRC，是失败的中间文件，不能作为最终色彩交付。

若新片在PotPlayer里仍明显更暗，先比较同一帧，再临时关闭该播放器的视频增强、检查单项亮度／对比度／gamma是否被调整，并对照另一种渲染器；每次只改一项并保留原值。[NVIDIA官方说明](https://www.nvidia.com/content/Control-Panel-Help/vLatest/en-us/mergedProjects/Display/Reference_Adjust_Video_Color_and_Image_Settings.htm)确认其视频gamma、动态对比、颜色增强与电平设置都能改变电影观感；选择由播放器控制可以排除驱动覆盖。不要为诊断重置全部设置，也不要盲目把所有电平切成Full。

目视范围：两版各12张全段代表帧、四处字幕边界共32张连续帧、4290–4305的16张连续人物近景，以及原生投影／AO／自身投影／线宽开关。已观察到刘海对额头的真实遮挡、身体与手臂明暗、地面投影和加厚轮廓，未在上述抽样中发现v2的下脸暗斑或字幕层级拆分。完整300帧做的是程序解码检查；不能把这些抽样说成每帧都经过人工美术评审。用户是否满意仍待反馈，PotPlayer具体配置与显示一致性也未验证。

1. 新目录运行只读探针，确认实际接收地面、演员材质响应和光源；阴影开关只是第一步。
2. 用本预设生成副本，检查同帧原生开关、鞋底、抬脚与衣服明暗；保持柔光和面部可读性。
3. `verify_caption_master.py --shadow-profile ... --graphic-profile ...` 独立重开检查。五官细节中未参与本轮分色的材质仍保留旧阈值，不能用身体新阈值误判它们。
4. `render_duet_sample.py` 渲染新300帧与独立beauty/actor缓存。
5. `finish_grounded_review.py` 等待原生渲染完成，合成固定层级字幕、指定原声和明确色彩的视频，执行视频／音轨／矩阵往返／拼接检查。
6. `package_grounded_review.py` 汇总真实对照、技术报告与离线预设库；人工检查记录另存，不以脚本通过代替美术判断。

新缓存和报告只写新目录，不修改用户GUI，不覆盖旧样片或源素材。人物仍为SDF与真实遮挡组合的美术卡渲，并非全身切成PBR；本轮也不包含全曲镜头校正。
